# project-reader — 项目深度阅读与分析

对新克隆或已有的项目进行全量分析，生成结构化报告，帮助快速理解项目架构和核心逻辑。

## 触发条件

- 手动：`/project-reader [项目路径]`
- 自动：用户消息包含"阅读项目""理解项目""分析项目""了解这个项目""project reader"

## 参数

| 参数 | 说明 |
|------|------|
| `[项目路径]` | 可选，默认为当前工作目录 |
| 无参数 | 分析当前目录下的项目 |

## 分析流程

### 第零步：识别项目类型 + 收集背景

1. 扫描项目目录，识别项目类型：
   - `.sh` 文件为主 → **Bash 项目** → 调用 `/bash-defensive-patterns`（知识）分析脚本质量
   - `.v` / `.sv` 文件为主 → **FPGA 项目** → 调用 `/verilog-sv-language` + `/vivado-synth`
   - `Makefile` / `CMakeLists.txt` 存在 → C/C++ 项目特征
   - `package.json` / `Cargo.toml` / `setup.py` 存在 → 按对应语言处理
   - 其他 → **通用项目**，自主分析
2. 读取项目已有的 `README.md`、`REVIEW.md`、`CHANGELOG*`（如有）
3. 读取本 skill 目录下的 `learnings.md`，获取历史分析经验

### 第一步：目录扫描与文件清单

1. 递归列出所有文件和目录，生成完整清单
2. 按文件类型分类统计（脚本/源码/文档/配置/数据）
3. 标注明显的关键文件（入口点、主配置、核心模块）

### 第二步：架构分析

1. 通过 `source`、`require`、`import`、文件引用等识别模块依赖关系
2. 绘制调用关系图（ASCII 格式）
3. 分析分层结构：入口层 → 业务层 → 基础/工具层
4. 识别数据流和控制流

### 第三步：关键文件详解

对每个核心文件：
- 文件用途概述
- 关键函数/模块及其职责
- 配置项（硬编码常量、可调参数）
- 接口约定（输入/输出、退出码、环境变量）
- 与其他文件的调用关系

### 第四步：依赖与运行环境

- 外部工具依赖清单（含版本要求）
- 运行平台/环境要求
- 构建/安装步骤
- 测试方式

### 第五步：使用指南

- 如何运行/启动项目
- 典型使用示例
- 常见配置修改点
- 注意事项

### 第六步：报告生成

在项目根目录创建 `doc_reader/`，生成以下文档：

```
doc_reader/
├── 00_项目概述.md           ← 一句话描述 + 用途 + 技术栈
├── 01_目录结构与文件清单.md  ← 完整文件树 + 分类统计
├── 02_架构设计.md            ← 分层架构 + 调用关系图 + 数据流
├── 03_关键文件详解.md        ← 每个核心文件的详细分析
├── 04_依赖与运行环境.md      ← 外部工具、版本、平台要求
└── 05_使用指南.md            ← 构建、运行、测试、常见修改
```

文档要求：
- **尽可能详细**：每个文件的功能、关键逻辑、配置项都写清楚
- **可操作**：读者看完能自己运行和修改项目
- **含代码引用**：引用具体文件:行号，方便定位

### 第七步：质量检查（调用 full-review 验证产物）

报告生成后，必须对 `doc_reader/` 下的产物进行质量检查，确保分析报告与实际项目代码一致。

1. 调用 `/full-review`，审查 `doc_reader/` 下的所有文档
2. full-review 会检查：
   - **配置值一致性**：报告中引用的默认值、路径是否与实际代码一致
   - **行号引用**：报告中的行号引用是否准确
   - **流程描述**：报告描述的流程是否匹配实际代码逻辑
   - **遗漏项**：实际代码中的重要内容是否在报告中缺失
3. 向用户展示发现的问题，等待确认后逐一修改

确认格式：
```
🔍 质量检查发现 X 个问题：
1. [03_关键文件详解.md] control.sh REBOOT_TIMEOUT 写成了 300，实际是 800
2. [02_架构设计.md] 调用关系图缺少初始 reboot 步骤
...

确认修改以上问题？
- 回复"是"→ 全部修改
- 回复"只改 X、Y..."→ 选择性修改
- 回复"否"→ 跳过所有修改
```

4. ⚠️ **必须等待用户明确回复后才执行修改**
5. 修改完成后，**重新调用 full-review 再次检查**，直到无新问题
6. **不限制迭代次数**，直到 full-review 报告 0 个问题

### 第八步：交互追问

报告通过质量检查后，主动提示：
```
✅ 分析报告已生成至 doc_reader/（已通过质量检查）

你可以：
- 回复"深入分析 <文件名>"→ 对该文件做更详细的分析
- 回复"调用关系"→ 生成更详细的调用链分析
- 回复"配置项汇总"→ 汇总所有配置文件中的可调参数
- 或者其他你想了解的问题
```

### 第九步：经验沉淀

分析完成后，检查是否有值得沉淀的经验。满足以下任一条件时，向用户提议追加到 `learnings.md`：

- **项目模式识别**：新识别出的项目结构模式（如特定的目录约定）
- **分析维度补充**：本次分析中发现值得加入标准分析清单的维度
- **用户偏好**：报告详略、聚焦方向等风格偏好

提议格式：
```
📝 建议沉淀到 project-reader 的经验：
1. [项目模式] <描述> — 来源：<项目名>
2. [分析维度] <描述> — 来源：<项目名>

确认写入 learnings.md？
- 回复"是"→ 全部写入
- 回复"只加 X"→ 选择性写入
- 回复"否"→ 跳过
```
⚠️ 必须经用户确认后才写入。无可沉淀经验则跳过。

## 输出格式

分析过程中，终端逐步展示分析进度。最终报告写入 `doc_reader/`，格式为 Markdown，含代码引用（文件:行号）。

## 行为准则

1. **全量分析不遗漏**：目录下所有文件都应纳入分析范围
2. **实事求是**：基于实际代码分析，不臆测不脑补
3. **调用合适 skill**：识别到特定项目类型时，主动调用对应 skill 辅助
4. **文档可操作**：生成的分析报告必须足够详细，读者看完能运行和修改
5. **质量检查不跳过**：第七步质量检查为强制步骤，必须调用 full-review 验证产物，迭代直到 0 问题
6. **修改需确认**：质量检查中发现的问题，修改前必须经用户确认
7. **交互但不强制**：报告通过检查后提示可追问，不替用户决定下一步
8. **经验需确认**：第九步的经验写入必须经用户确认
