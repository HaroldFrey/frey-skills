## Skill 的本质理解

### Skill 是什么

Skill 本质上是**给 AI 的一段预置指令**。当触发条件满足时，这段指令会被注入到 AI 的上下文中，AI 按照指令执行。

```
你创建 Skill → 存为 skill.md → AI 读取 → 照指令执行
```

### 核心认知

| 认知 | 说明 |
|------|------|
| **Skill ≠ 程序** | Skill 不是代码，是自然语言指令。AI 会"理解"并执行，不是编译运行 |
| **Skill = SOP** | 就像给新人写的标准操作流程（SOP），越清晰越不易出错 |
| **越具体越好** | "检查代码"不如"用 grep 搜索 TODO，检查是否有未完成的占位符" |
| **边界要明确** | 说清楚 skill 做什么、不做什么，防止 AI 越权操作 |

## 目录结构与命名

### 正确的目录结构（血的教训）

```
skills/
├── <skill-name>/          ← 必须是子目录！文件夹名 = 命令名
│   ├── skill.md            ← 文件名固定，不能改
│   ├── 使用说明.md          ← 人类可读文档，每个 skill 都要有
│   ├── references/         ← 可选：参考资料（规范、手册等）
│   └── examples/           ← 可选：示例项目
```

> ⚠️ **直接放 `skills/ls.md` 不生效！** 必须是 `skills/ls/skill.md`。这是新手最常见的错误。

### 命名规范

| 规则 | 正确 ✅ | 错误 ❌ |
|------|---------|---------|
| 小写字母 + 连字符（kebab-case） | `git-push`, `bash-dev-workflow` | `git_push`, `BashDevWorkflow` |
| 简短但有描述性 | `req-analysis` | `ra`（太短，含义不明） |
| 避免特殊字符 | `vivado-tcl` | `vivado&tcl`, `vivado tcl` |
| 文件夹名 = 命令名 | 文件夹叫 `git-push` → `/git-push` | 文件夹叫 `gitpush` 但想用 `/git-push` |

### 关于斜杠命令匹配

- 自定义 skill 需要**精确匹配全名**：`/git` 不会自动补全为 `/git-push`
- 改名后如果匹配不生效，**重启 VSCode** 试试
- `/reload-skills` 重新加载 skill 列表，但某些匹配缓存可能需要重启

## Frontmatter 设计

### 必须字段

```yaml
---
name: skill-name           # 必须：与文件夹名一致
description: 简短描述       # 必须：用于 AI 自动匹配，含触发关键词
---
```

### Description 编写技巧

`description` 有两个作用：
1. 在 `/skills` 列表中展示
2. AI 根据它判断何时自动调用此 skill

**好的 description**：
```yaml
description: 将本地仓库推送到 GitHub。自动检测 git 仓库状态，生成 commit message，推送到远程仓库。触发词：推送、推送代码、push、git push、github push。
```

**不好的 description**：
```yaml
description: 推送代码         # 太短，AI 无法准确匹配
```

关键原则：
- 包含**触发关键词**（中英文都要有）
- 描述**做什么**而非**是什么**
- 结尾可明确列出触发词

## 四种 Skill 类型的设计模式

### 类型 1：执行型（简单命令）

**特点**：单一动作，输入即输出，无需确认

**代表**：`/pwd`, `/ls`, `/skills`

**设计模板**：
```markdown
---
name: xxx
description: 简要描述 + 触发词
---

当用户调用这个 skill 时，执行以下操作：
1. 第一步
2. 第二步
3. 以清晰的格式输出结果
```

**要点**：
- 指令清晰简短
- 输出格式明确指定
- 无需检查点

### 类型 2：知识型（参考手册）

**特点**：不执行动作，只注入知识到 AI 上下文

**代表**：`verilog-sv-language`, `bash-defensive-patterns`, `vivado-synth`

**设计模板**：
```markdown
---
name: xxx
description: 知识领域 + 触发词
---

# 标题

## 规则/知识点 1
<详细说明 + 代码示例>

## 规则/知识点 2
<详细说明 + 代码示例>

...

## 行为准则
1. ...
2. ...
```

**要点**：
- 结构清晰，按规则/知识点编号
- 每个知识点配代码示例（正确 vs 错误）
- 末尾有行为准则，告诉 AI 如何应用这些知识
- 适合被其他 skill 调用（如编码阶段注入规范）

### 类型 3：分析型（结构化分析）

**特点**：多步骤分析，生成结构化报告，有质量检查循环

**代表**：`full-review`, `project-reader`

**设计模板**：
```markdown
## 分析流程

### 第一步：...
### 第二步：...
...
### 第 N 步：质量检查（必须调用 full-review 验证）
### 第 N+1 步：交互追问
### 第 N+2 步：经验沉淀

## 行为准则
```

**要点**：
- 输出格式要明确（报告模板、分级标准）
- 内部调用知识型 skill 获取规范
- 质量检查是强制步骤，迭代直到通过
- 支持 `--focus` 等参数缩小范围

### 类型 4：编排型/流程型（多阶段工作流）

**特点**：多个阶段串联，有检查点，支持自动/手动模式

**代表**：`bash-dev-workflow`, `sv-dev-workflow`, `skill-maker`

**设计模板**（详见下一节）。

## Workflow 型 Skill 设计要点

### 阶段划分原则

```
需求分析 → 设计 → 编码 → 审查 → 追踪 → 迭代 → 最终检查
```

- 每个阶段有**明确的输入和输出**
- 阶段之间用 **🛑 检查点** 分隔（手动模式暂停）
- 需求分析阶段**永远是强制手动确认**，不受 `--auto` 影响

### 检查点（Checkpoint）设计

```markdown
### 阶段 N：XXX

... 执行逻辑 ...

> ⚠️ **必须用户确认后才进入下一阶段。** 不受任何模式影响。
```

检查点分为两种：

| 类型 | 标记 | 行为 |
|------|:--:|------|
| **强制手动** | 🛑 | 任何时候都必须等待用户确认（如需求分析、设计方案） |
| **模式相关** | 🔧/🤖 | 手动模式暂停，自动模式跳过 |

### 设计-代码绑定

在 workflow 中，设计方案中的每个编号步骤对应代码中的编号注释：

```
设计方案：                   代码：
1. 参数解析                  # ---- 1. 参数解析 ----
2. 环境检查                  # ---- 2. 环境检查 ----
3. 核心逻辑                  # ---- 3. 核心逻辑 ----
```

好处：审查时可以逐条对照，不会遗漏。

### 多文件项目支持

```markdown
## 项目类型判断

- 单文件：所有代码在一个脚本中
- 多文件：script/ 目录 + lib/ 目录

多文件项目的额外步骤：
- 每个文件独立审查
- 增加集成审查（文件间接口、调用链）
```

### 设计方案文档模板

设计方案至少包含 10 个部分：

1. 项目概述
2. 需求列表
3. 设计思路（需求→方案→架构→实现→优缺点→扩展，每个子项要详细）
4. 模块划分
5. 接口定义
6. 数据流
7. 关键实现细节
8. 边界条件与错误处理
9. 测试策略
10. 依赖与运行环境

> ⚠️ "脚本设计思路"不能随便讲讲。必须覆盖：需求→方案→架构→实现→优缺点→扩展，每个子项都要详细展开。

## 手动/自动模式设计

### 默认手动，自动需显式声明

```markdown
| 模式 | 触发 |
|------|------|
| 🔧 手动（默认） | 不指定 |
| 🤖 自动 | `--auto` / "自动" / "全自动" |
```

### 阶段行为表

手动模式下的 workflow 必须明确标注每个阶段在两种模式下的行为。

### 需求确认永不自动

```
> ⚠️ 需求确认阶段无论手动/自动都必须人工确认。
```

这是安全底线——AI 不能替用户决定"需求是否正确"。

## Skill 间调用关系

### 调用链设计

```
编排型 Skill（高层）
    │
    ├── 调用 知识型 Skill（注入规范）
    ├── 调用 分析型 Skill（质量检查）
    └── 内嵌 预处理 Skill 的逻辑
```

### 实际调用关系示例

| 父 Skill | 调用的子 Skill | 调用时机 |
|---------|---------------|---------|
| `bash-dev-workflow` | `bash-defensive-patterns` | 编码阶段 |
| `sv-dev-workflow` | `verilog-sv-language` | 编码(A2) + 审查(A3) |
| `sv-dev-workflow` | `vivado-synth` | 最终审查(A6) |
| `full-review` | `bash-defensive-patterns` | Bash 项目审查 |
| `full-review` | `verilog-sv-language` + `vivado-synth` | Verilog 项目审查 |
| `project-reader` | `bash-defensive-patterns` | Bash 项目分析 |
| `project-reader` | `verilog-sv-language` + `vivado-synth` | FPGA 项目分析 |
| `project-reader` | `full-review` | 分析产物质量检查 |

### 调用原则

- **知识型 skill 不调用其他 skill**（叶子节点）
- **编排型 skill 调用知识型/分析型**（高层调用低层）
- **避免循环调用**
- **调用关系写入 README.md 和 skill 使用说明**

## 文档规范

### 每个 Skill 必须有两份文档

| 文档 | 读者 | 内容 |
|------|------|------|
| `skill.md` | AI | 指令、流程、行为准则 |
| `使用说明.md` | 人 | 功能、用法、示例、联动 |

### 使用说明模板

```markdown
# /skill-name — 一句话描述

## 功能
...

## 触发方式
- 手动：`/skill-name`
- 自动匹配：说"关键词1"、"关键词2"

## 使用示例
...

## 工作流程
...

## 参数（如有）
| 参数 | 说明 |
|------|------|
```

### 项目文档命名（中文）

在 workflow 中生成的项目文档使用中文命名：

| 文档 | 文件名 |
|------|--------|
| 设计方案 | `设计方案_<项目名>.md` |
| 语法解析 | `语法解析_<项目名>.md` |
| 审查报告 | `审查报告_<项目名>.md` |
| 问题追踪 | `问题追踪_<项目名>.md` |
| 最终报告 | `最终报告_<项目名>.md` |

### README.md 维护

skills 目录下的 `README.md` 是 skill 目录。每次增/删/改 skill 后必须同步更新：
- 新增 skill → 添加表项 + 详细说明
- 改名 → 更新所有引用
- 改功能 → 更新说明文字
- 调用关系图要同步更新

## 权限与配置

### 减少权限弹窗

如果 skill 需要频繁访问某个目录/命令，在 `settings.json` 中预先配置权限：

```json
{
  "permissions": {
    "allow": [
      "Bash(git:*)",
      "Bash(npm:*)",
      "Read(C:\\Users\\28968\\.claude\\skills\\*)",
      "Edit(C:\\Users\\28968\\.claude\\skills\\*)",
      "Write(C:\\Users\\28968\\.claude\\skills\\*)"
    ]
  }
}
```

### MCP 配置位置

- ❌ `mcpServers` 不能放在 `settings.json`（会报验证错误）
- ✅ MCP 配置放 `.mcp.json` 文件

## 测试与调试

### 测试流程

1. 创建/修改 skill 后，用 `/reload-skills` 刷新
2. 输入 `/skill-name` 测试手动触发
3. 输入描述性语句测试自动匹配
4. 如果自动匹配不生效，**重启 VSCode**
5. 检查 `/skills` 列表中是否出现该 skill

### 常见调试手段

| 问题 | 排查方向 |
|------|---------|
| `/命令` 显示 Unknown | 检查目录结构（是否是 `skills/name/skill.md`？） |
| 自动匹配不触发 | 检查 `description` 是否包含触发关键词 |
| 改名后旧名还能用 | 旧目录是否删除？重启 VSCode |
| AI 不按指令执行 | 指令是否够具体？是否被其他 skill 干扰？ |

## 常见踩坑

### 坑 1：目录结构错误
```
❌ skills/ls.md                    → /ls 不生效
✅ skills/ls/skill.md              → /ls 正常
```

### 坑 2：Frontmatter 格式错误
```yaml
❌ name: my skill                  → 不能有空格
❌ name：my-skill                  → 用了中文冒号
✅ name: my-skill                  → 英文冒号 + 空格
```

### 坑 3：Description 不含触发词
```yaml
❌ description: 一个工具             → AI 不知道怎么匹配
✅ description: 列出文件目录。触发词：ls、列出文件、显示目录、文件列表
```

### 坑 4：检查点被跳过
在自动模式下，指令中没明确标注"不受模式影响"的检查点可能被 AI 跳过。需求确认等关键检查点必须加：
```markdown
> ⚠️ **必须用户确认后才继续。不受任何模式影响。**
```

### 坑 5：指令过于模糊
```markdown
❌ 检查代码质量             → AI 不知道怎么检查
✅ 用 grep 搜索 TODO/FIXME，检查是否有硬编码密码，检查退出码是否被忽略...
```

### 坑 6：忘了生成使用说明
每个 skill 目录下必须有 `使用说明.md`。用户看不懂 `skill.md` 里的指令——那是写给 AI 的。

### 坑 7：Skill 名称与已有冲突
项目级 skill 会覆盖同名的全局 skill。确保命名唯一，或明确这是有意覆盖。

### 坑 8：VSCode 扩展 vs CLI 的误解
- 扩展和 CLI 都能用自定义 skill，**互不依赖**
- 扩展 ≠ CLI 的外壳
- 两者共享 `skills/` 目录

## 维护与迭代

### Skill 的生命周期

```
创建 → 试用 → 反馈 → 迭代 → 稳定使用 → 持续改进
```

### 什么时候该修改 Skill

- 用户反馈"不好用"/"不准确"
- 发现了新的使用场景
- 需要联动新的 skill
- 文档过时或示例不足

### 经验沉淀

每做一个新 skill，问自己：
- 这次学到了什么之前不知道的？
- 有没有可复用的模式？
- 有没有踩了新的坑？
- 现有的 skill 是否需要同步更新？

将新发现追加到本文档。

## 快速自检清单

制作新 skill 前，逐条确认：

- [ ] 目录结构：`skills/<name>/skill.md`（不是 `skills/<name>.md`）
- [ ] Frontmatter：`name` + `description`（含触发词）
- [ ] Skill 类型明确（执行/知识/分析/编排）
- [ ] 如果是 workflow，检查点标注清晰（🛑）
- [ ] 手动模式是否默认？需求确认是否强制手动？
- [ ] 生成了 `使用说明.md`
- [ ] 是否需要调用其他 skill？
- [ ] 是否需要预设权限？
- [ ] `/reload-skills` 测试通过
- [ ] 更新了 skills/README.md
- [ ] 行为准则编号清晰
