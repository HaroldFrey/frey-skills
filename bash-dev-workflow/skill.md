# Bash 脚本开发全流程

编排型 skill，管理从设计方案到最终交付的完整开发流程。**自动适配单文件和多文件项目。**

---

## 项目规模判定

流程开始前先判断规模：

| 规模 | 条件 | script/ 结构 | 审查策略 |
|------|------|-------------|---------|
| 单文件 | 功能简单，≤ 200 行 | `script/<脚本名>.sh` | 1 次审查 |
| 多文件 | 功能复杂，或用户指定拆分 | `script/main.sh` + `script/lib/*.sh` | 每个文件独立审查 + 集成审查 |

**判定方式**：AI 在阶段 1 设计时根据需求复杂度自动判断，并询问用户确认。用户也可以直接说"拆成多个文件"。

## 目录约定

### 单文件
```
<工作目录>/
├── README.md
├── script/
│   └── <脚本名>.sh
└── doc/
    ├── 需求分析_<脚本名>.md
    ├── 设计方案_<脚本名>.md
    ├── 语法解析_<脚本名>.md
    ├── 审查报告_<脚本名>.md
    ├── 问题追踪_<脚本名>.md
    └── 最终报告_<脚本名>.md
```

### 多文件
```
<工作目录>/
├── README.md
├── script/
│   ├── main.sh                  ← 主入口
│   └── lib/
│       ├── logging.sh           ← 日志模块
│       └── validate.sh          ← 校验模块
└── doc/
    ├── 设计方案_<项目名>.md      ← 含文件划分表
    ├── 语法解析_<项目名>.md      ← 跨文件调用图
    ├── 审查报告_<项目名>.md      ← 每个文件 + 集成审查
    ├── 问题追踪_<项目名>.md
    └── 最终报告_<项目名>.md
```

流程开始：
```bash
mkdir -p script/lib doc
```

## 启动：选择模式

> ⚠️ **默认强制使用手动模式。自动模式有风险——AI 可能在审查时遗漏问题。**
> **只有用户明确说出 `--auto` / "自动" / "全自动" / "自动模式" 时，才可进入自动模式。**
> **绝对禁止 AI 自作主张进入自动模式。**

流程开始时必须先询问：

```
请选择模式：
  🔧 手动模式 — 每个阶段暂停等待审核确认（默认，推荐）
  🤖 自动模式 — AI 自行审查推进，仅在最终汇报

回复 "自动" / "--auto" 进入自动模式，否则使用手动模式。
```

| 模式 | 触发条件 | 检查点行为 |
|------|---------|-----------|
| 🔧 **手动（默认）** | 用户未明确要求自动 | 每个 🛑 暂停，**必须用户回复"通过"才能继续** |
| 🤖 自动 | 用户明确说 `--auto` / "自动" / "全自动" | AI 自行审查，最终汇报。**但需求确认仍必须人工** |

## 流程概览

### 单文件
```
需求分析 → 设计 → 编码+语法 → 审查 → 追踪 → [迭代] → 最终 → 全面检查 → README
      ↑                                                        │
      └──────────── 用户修改需求时回到需求分析 ──────────────────┘
```

### 多文件
```
需求分析 → 设计(含文件划分)
    │
    ▼
┌─────────────────────────────────────────────┐
│ 对每个文件（按依赖顺序）：                     │
│   编码该文件 → 审查该文件 → 通过 → 下一个      │
└─────────────────────────────────────────────┘
    │
    ▼
  集成审查（跨文件一致性）
    │
    ▼
  追踪 → [迭代] → 最终 → 全面检查 → README
```

## 阶段 0：需求分析（REQUIREMENTS）🆕

> **需求没搞清楚之前，绝对禁止进入设计阶段。**

### AI 需要做的事

1. 理解用户最初的需求描述

2. **不断追问**，直到所有问题都有明确答案。不限轮次，每次可问任意数量问题：
   - 脚本要解决什么具体问题？输入/输出是什么？
   - 运行平台？依赖限制？单文件还是多文件？
   - 边界条件？错误处理策略？
   - ...（根据具体需求灵活提问）

3. **直到所有细节明确，且用户说"可以了"或"开始设计"**，才进入下一阶段

4. 生成需求文档 `doc/需求分析_<项目名>.md`

### 需求文档模板
```markdown
# 需求分析 — <项目名>
## 项目目标 | ## 功能需求(编号+优先级) | ## 非功能需求
## 输入输出规格 | ## 边界条件与约束 | ## 用户确认(checkbox)
```

> ⚠️ **此检查点不受模式影响——即使自动模式也必须等待用户确认。需求错了，后面全错。**

🛑 **强制检查点**：展示需求文档 → **必须**用户确认后才可进入阶段 1

### 需求变更
开发中用户修改需求 → 暂停当前 → 回到阶段 0 更新需求文档 → 逐阶段重新推进

## 阶段 1：设计方案（DESIGN）

### AI 需要做的事

1. **基于阶段 0 已确认的需求文档进行设计**，无需重新询问需求

2. 生成设计文档 `doc/设计方案_<项目名>.md`，必须包含以下全部章节：

```markdown
# 设计方案 — <项目名>

> **设计方案是第一道质量关口。必须足够详细，让用户仅阅读此文档即可判断设计是否正确，无需查看代码。**

## 功能概述
<一句话描述 + 一段展开说明脚本的用途、使用场景、目标用户>

## 脚本设计思路
<必须包含以下 6 个子节>

### 需求与目标
- 脚本要解决什么具体问题？目标用户是谁？在什么场景下使用？
- 核心功能和非功能需求（性能、可移植性、零依赖等）

### 方案选型
- 候选方案对比表（如 Bash vs Python vs Go，至少 2 个方案，列出优缺点和选择理由）
- 关键技术的选型理由（awk vs bc、source vs 子进程、单文件 vs 多文件）
- 每个决策的量化依据

### 架构设计
- 整体架构层次（入口层 → 业务层 → 基础层），用 ASCII 框图标注
- 各模块职责和边界
- 数据流和控制流的完整走向

### 具体实现要点
<对每个关键技术点展开>
- 关键算法的实现方式（含伪代码或公式）
- 平台兼容性处理（每个平台分支的具体命令差异）
- 错误处理和边界情况的应对策略（含具体场景）

### 方案优劣分析
- 本方案的优点（至少 3 条，含量化数据）
- 本方案的局限（至少 3 条）
- 与替代方案的量化对比

### 改进与扩展
- 当前版本的改进点和后续可扩展方向
- 已知技术债务
```

## 阶段 2：编写代码（CODE）

### 单文件

1. 加载 `bash-defensive-patterns`
2. 编写 `script/<脚本名>.sh`，含 14 条规范
   - **代码注释必须与设计方案"脚本内部流程"的编号步骤一一对应**
   - 每个步骤起始处加 `# N. <步骤描述>` 注释块

3. 生成 `doc/语法解析_<脚本名>.md`

🛑 检查点 → 进入阶段 3

### 多文件

**按设计文档的依赖顺序逐个编写**：

```
对第 1 个文件（最先被依赖的，如 lib/logging.sh）：
  1. 加载 bash-defensive-patterns
  2. 编写该文件
     - **代码注释必须与设计方案"各脚本详细说明"中该文件的编号步骤一一对应**
     - 每个步骤起始处加 `# N. <步骤描述>` 注释块
  3. 🛑 检查点（该文件通过后继续）

对第 2 个文件（如 lib/validate.sh）：
  1. 编写该文件（同上，注释与设计步骤一一对应）
  2. 🛑 检查点

... 直到所有文件编写完成

最后：生成 doc/语法解析_<项目名>.md
  → 对每个文件仅记录关键语法（不逐行解析）
  → 重点：跨文件调用图
🛑 检查点 → 进入阶段 3
```

## 语法解析文档（SYNTAX）

### 单文件 — 同原规则

### 多文件 — 侧重跨文件关系

```markdown
# 语法解析 — <项目名>

## 总体行数
| 文件 | 行数 |
|------|------|
| script/main.sh | 120 |
| script/lib/logging.sh | 45 |
| script/lib/validate.sh | 60 |
| **合计** | 225 |

## 跨文件调用图
```
main.sh
  ├── source lib/logging.sh → log_info(), log_warn(), log_error()
  └── source lib/validate.sh → validate_file(), validate_dir()
```

## 各文件关键语法
### main.sh
- L30: trap 链式清理（ERR + EXIT 两级）
- L50: while+case 参数解析模式

### lib/logging.sh
- L10: printf 带时间戳格式化

### lib/validate.sh
- L15: [[ -f ]] 与 [[ -r ]] 组合检查

## 更新记录
...
```

**同步规则**：每次任何文件变动，更新对应文件的语法条目 + 行数 + 调用图。

## 阶段 3：代码审查（REVIEW）

| 维度 | 检查项 |
|------|--------|
| 安全性 | 命令注入、临时文件、权限 |
| 正确性 | 逻辑与设计一致、边界覆盖 |
| 健壮性 | 错误处理、trap、输入校验 |
| 规范性 | bash-defensive-patterns 14 条 |
| 可维护性 | 注释、命名、结构 |
| 可移植性 | GNU vs BSD 兼容 |

### 单文件

1 份审查 → `doc/审查报告_<项目名>.md` → 🛑 检查点

### 多文件

```
对每个文件 → 独立审查（L1~L6 维度）
    ↓
集成审查（额外维度）：
  | 接口一致 | source 路径正确？函数签名匹配？ |
  | 无循环依赖 | A→B 和 B→A 不同时存在？ |
  | 命名无冲突 | 全局变量/函数跨文件不重复？ |
  | 错误传播 | 子脚本失败后主脚本能否感知？（set -e + trap） |
  | 加载顺序 | source 顺序是否满足依赖？（被依赖的先加载） |
    ↓
全部写入 doc/审查报告_<项目名>.md → 🛑 检查点
```

```markdown
### P-001：<概述>
- **所属文件**：script/lib/validate.sh
- **严重程度**：🟡中
- ...
```

🛑 检查点

## 阶段 5：迭代（ITERATE）

### 规则（单文件 + 多文件通用）

```
待解决问题 → 回阶段 1（设计）→ 🛑
         → 仅修改受影响的文件 → 🛑
         → 单文件：重新审查 → 🛑
         → 多文件：重新审查受影响文件 + 重新集成审查 → 🛑
         → 更新追踪 → 🛑
         → 仍有问题 → 新一轮迭代
```

**多文件特别注意**：修改一个文件后，必须检查是否影响其他文件的接口。如果接口变了，同步修改调用方。

**自动模式**：最多 3 轮。

---

## 阶段 6：最终审查（FINAL）

1. 完整性检查
2. 14 条规范逐条（多文件时所有文件归并检查）
3. 静态分析（shellcheck，多文件时逐个检查）
4. 测试场景
5. 生成 `doc/最终报告_<项目名>.md`

🛑 检查点

---

## 阶段 7：全面一致性检查（VERIFY）

### 单文件 — 同原规则

### 多文件 — 额外检查项

| 检查项 | 方法 |
|--------|------|
| 文件划分与设计一致 | 设计文档文件划分表 vs script/ 实际文件 |
| 跨文件接口一致 | 设计文档接口约定表 vs 实际 source + 调用 |
| 无遗漏 source | shellcheck 或 grep 确认所有调用方 source 了对应 lib |
| 语法解析调用图准确 | SYNTAX 调用图 vs 实际 source 关系 |
| 各文件行数与文档一致 | wc -l 每个文件 vs 文档记录 |
| 交付物完整 | 所有文件 + doc 全部存在 |

🛑 检查点 → 生成/更新 README

## 阶段 8：经验沉淀（LEARN）

开发流程结束后，检查本次是否有值得沉淀的经验。满足以下任一条件时，向用户提议追加到 `learnings.md`：

- 流程层面：某个阶段步骤需要调整/简化
- 错误模式：本轮反复出现的代码错误类型
- 用户偏好：审批粒度、auto 模式边界、文档详略等

提议格式：
```
📝 建议沉淀到 bash-dev-workflow 的经验：
1. [流程改进] <描述>
2. [常见错误] <描述>
3. [用户偏好] <描述>

确认写入 learnings.md？
- 回复"是"→ 全部写入
- 回复"只加 X"→ 选择性写入
- 回复"否"→ 跳过
```
⚠️ 必须经用户确认后才写入。无可沉淀经验则跳过。此阶段在 README 生成后执行。

## 行为准则

1. **默认手动模式**：只有用户明确说 `--auto` / "自动" / "全自动" 才进入自动模式。禁止 AI 自作主张
2. **需求没搞清楚之前禁止进入设计**：先执行阶段 0 需求分析，追问直到需求完全理清楚，直到用户确认
3. **用户修改需求 → 立即回到阶段 0**，更新需求文档后逐阶段重新推进
4. 启动问模式 + 判定单文件/多文件规模
3. 创建目录：`mkdir -p script/lib doc`
4. **多文件时按依赖顺序逐个编写审查，全部完成后做集成审查**
5. 迭代从设计开始，只改受影响文件，修改后同步检查接口一致性
6. 加载 bash-defensive-patterns、文档实时写入、自动模式 ≤3 轮
