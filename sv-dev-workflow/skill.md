# Verilog/SystemVerilog 模块开发全流程

编排 RTL 模块 + 测试平台两阶段开发。RTL 完成后自动进入测试平台开发。

---

## 项目规模判定

流程开始前先判断规模：

| 规模 | 条件 | rtl/ 结构 | 审查策略 |
|------|------|---------|---------|
| 单模块 | 功能简单，单一时钟域 | `rtl/<模块名>.sv` | 1 次审查 |
| 多模块 | 功能复杂，含子模块 | `rtl/<top>.sv` + `rtl/<sub1>.sv` + `rtl/<sub2>.sv` | 每个模块独立审查 + 集成审查 |

**判定方式**：AI 在 A1 设计时自动判断并询问用户确认。

## 启动：选择模式

> ⚠️ **默认强制使用手动模式。自动模式有风险——AI 可能在审查时遗漏问题。**
> **只有用户明确说出 `--auto` / "自动" / "全自动" / "自动模式" 时，才可进入自动模式。**
> **绝对禁止 AI 自作主张进入自动模式。**

流程开始时必须先询问：

```
请选择模式：
  🔧 手动模式 — 每个阶段暂停等待审核确认（默认，推荐）
  🤖 自动模式 — AI 自行审查推进，仅在最终汇报

回复 "自动" / "--auto" 进入自动模式，否则使用手动模式。
```

| 模式 | 触发条件 | 检查点行为 |
|------|---------|-----------|
| 🔧 **手动（默认）** | 用户未明确要求自动 | 每个 🛑 暂停，**必须用户回复"通过"才能继续** |
| 🤖 自动 | 用户明确说 `--auto` / "自动" / "全自动" | AI 自行审查，最终汇报。**但 A0/B0 需求确认仍必须人工** |

## 总流程

```
Phase A: RTL
  判断规模 → A0 需求分析 → A1 设计 → A2 编码+语法 → A3 审查循环(代码级+full-review, 直到通过) → A4 追踪 → A5 迭代 → A6 最终 → A7 检查
                ↑                                                                  │
                └──────────────── 用户修改需求时回到 A0 ────────────────────────────┘
    ↓ 交付
Phase B: Testbench
  B0 需求分析 → B1 设计 → B2 编码+语法 → B3 审查循环(直到通过) → B4 追踪 → B5 迭代 → B6 最终 → B7 检查
    ↓ 交付
Phase C: 仿真验证循环（大阶段）
  C0 环境与脚本准备 → C1 编译+仿真 → C2 波形分析 → C3 问题定位与修复 → C4 回归
    │                                                          ↑
    │      C1/C2 发现问题 → C3 四分类回退: 方案设计 A1 / 编码 A2 / TB与脚本 B2 / 工具兼容就地绕过
    └───────────────────────────────────────────────────────────┘
  终止条件满足（ALL PASS + 脚本全过 + 连续一轮无新问题）
    ↓
  C5 全面检查 → README
```

# Phase A：RTL 模块开发

---

## A0. 需求分析（REQUIREMENTS）🆕

> **需求没搞清楚之前，绝对禁止进入设计阶段。**

### AI 需要做的事

1. 理解用户最初的需求描述

2. **不断追问**，不限轮次，每次可问任意数量问题：
   - 模块功能？接口类型？时钟域？
   - 性能指标（吞吐/延迟/频率）？资源预算？
   - 参数化范围？复位策略？目标器件？
   - 是否需要 testbench？
   - ...（根据具体需求灵活提问）

3. **直到所有细节明确，且用户说"可以了"或"开始设计"**，才进入下一阶段

4. 生成需求文档 `doc/rtl/需求分析_<模块名>.md`

### 需求文档模板
```markdown
# 需求分析 — <模块名>
## 功能目标 | ## 功能需求(编号+优先级) | ## 接口规格 | ## 非功能需求
## 性能指标 | ## 约束条件 | ## 用户确认(checkbox)
```

> ⚠️ **此检查点不受模式影响——即使自动模式也必须等待用户确认。需求错了，后面全错。**

🛑 **强制检查点**：展示需求文档 → **必须**用户确认后才可进入 A1

### 需求变更
开发中用户修改需求 → 暂停当前 → 回到 A0 更新需求文档 → 逐阶段重新推进

## A1. 微架构设计 → `doc/rtl/设计方案_<模块名>.md`

1. **基于 A0 已确认的需求文档进行设计**，无需重新询问需求
2. 生成设计文档，必须包含以下**全部**章节：

```markdown
# 设计方案 — <模块名>

> **设计方案是第一道质量关口。必须足够详细，让用户仅阅读此文档即可判断设计是否正确，无需查看代码。**

## 功能概述
<一句话描述 + 一段展开说明模块的用途、使用场景、在系统中的位置>

## 设计思路
<必须包含以下 6 个子节>

### 需求与目标
- 模块要解决什么具体问题？在什么场景下使用？
- 关键性能指标（吞吐量、延迟、最高时钟频率、资源预算）
- 非功能需求（可移植性、可测试性、可配置性）

### 方案选型
- 候选方案对比表（至少 2 个方案，列出优缺点和选择理由）
- 关键技术取舍及依据：
  - 流水线深度 vs 延迟 vs 面积
  - 同步 vs 异步设计
  - FSM 编码方式（one-hot / binary / gray）
  - 存储方式（Distributed RAM vs Block RAM vs 寄存器）
- 多模块拆分的决策依据（如有拆分）

### 架构设计
- 顶层框图（ASCII art，标注信号名和位宽）
- 各子模块职责和边界（输入/输出/处理内容）
- 数据流走向（从输入端口到输出端口的完整路径）
- 控制流走向（状态机如何驱动数据流）

### 具体实现要点
<对每个关键技术点展开说明>
- 关键算法的硬件实现方式（含公式或伪代码）
- CDC 处理策略（同步器级数、ASYNC_REG、格雷码转换细节）
- 综合属性使用计划（每个属性的位置和原因）
- 时序/面积的权衡（关键路径逻辑级数预估、如何优化）
- 复位策略（同步/异步、复位值、复位释放时序）

### 方案优劣分析
- 本方案的优点（至少 3 条）
- 本方案的局限（至少 3 条，含适用条件）
- 与替代方案的量化对比（如：方案 A 延迟 5 周期面积 100LUT vs 方案 B 延迟 3 周期面积 200LUT）

### 改进与扩展
- 当前版本未实现但值得考虑的改进点
- 后续可扩展的功能方向
- 已知技术债务
```

## A3. 综合审查 → `doc/rtl/审查报告_<模块名>.md`（循环直到通过）

> **审查是迭代的：发现问题 → 修复 → 重新审查（回归），直到所有审查维度通过为止。单次审查不能视为完成。**

**步骤 1：代码级审查（调用 `verilog-sv-language`，保留）**

| 维度 | 检查项 |
|------|--------|
| 可综合性 | initial/fork/#delay？ |
| 锁存器风险 | always_comb 默认赋值？case default？ |
| 规范符合 | verilog-sv-language 逐条 |
| CDC 安全 | 同步器？ASYNC_REG？ |
| 关键路径 | 逻辑级数？ |
| 复位安全 | 覆盖？ |

### 多模块

**每个模块独立审查 + 集成审查（额外维度）：**

| 检查项 | 方法 |
|--------|------|
| 端口映射一致 | 顶层实例化端口 vs 子模块声明端口逐位对照 |
| 参数传递正确 | 顶层 parameter 传递值 vs 子模块默认值 |
| 无悬空输入 | 子模块输入端口是否全部连接？ |
| 位宽匹配 | 顶层连线位宽 vs 子模块端口位宽 |
| 时钟/复位一致 | 所有模块是否使用相同的时钟和复位方案？ |

审查报告含"所属模块"列。

**步骤 2：补充审查（调用 `full-review`，新增）**

代码级审查通过后，调用 `full-review` 对本阶段产出做补充检查，侧重代码级审查不覆盖的维度：

| 补充维度 | 检查项 |
|---------|--------|
| 文档一致性 | RTL ↔ 设计方案/需求分析（端口/FSM/参数/行数引用） |
| 资源预估 | dist-RAM/BRAM 的 FF/LUT 消耗是否按综合实现核对 |
| 测试覆盖缺口 | 数据内容比对是否有效（expected 数组是否被使用、计数器是否越界） |
| 跨文件契约 | 生成脚本 ↔ 样本 RTL 一致性、文档 ↔ 代码参数一致 |
| 错误处理 | 边界条件（空输入、超范围、超容量告警） |

full-review 发现的问题写入同一份审查报告（标注来源为 full-review），并按其流程输出报告。

**循环规则（审查直到通过）：**

```
┌─────────────────────────────────────────────────────┐
│  A3 审查循环                                          │
│                                                      │
│  1. 代码级审查（verilog-sv-language）                 │
│  2. 补充审查（full-review）                           │
│      ↓                                                │
│  发现问题？ ──否──→ 审查通过，进入 A4 🛑              │
│      │是                                             │
│      ↓                                                │
│  记录问题（问题追踪_<模块名>.md）                      │
│  修复（多模块时只改受影响模块）                        │
│  重新审查（回归，重复步骤 1+2）                       │
│      ↑_____________________________│                 │
└─────────────────────────────────────────────────────┘
```

- **循环终止条件**：连续一轮步骤 1 + 步骤 2 均无新问题 → 审查通过
- 每轮循环记录到审查报告（标注"第 N 轮审查"），问题追踪同步更新
- 多模块时每轮循环必须重新执行集成审查
- 修复涉及 RTL 代码时，从 A1 设计方案对应章节核对受影响范围（避免只改代码不改文档）

🛑 检查点（审查通过后）

# Phase B：测试平台开发

# Phase C：仿真验证循环（大阶段）

> 静态审查（A3/B3）只能发现静态问题（可综合性、锁存器、规范），无法发现动态问题
> （竞态、X 态、握手时序、跨时钟域）。本阶段把 **编译 → 仿真 → 波形生成 → VCD 分析
> 脚本 → 波形分析 → 发现问题 → 修复** 作为一个循环整体执行，直到全部通过。

---

## C0. 环境与脚本准备

1. 检查工具链：`iverilog` / `vvp` / `gtkwave` / `python`（缺失先提示安装）
2. 若 `sim/` 下没有 VCD 分析脚本（如 `check_vcd.py`），先编写：
   - 仅用 **Python 标准库**，不依赖第三方包
   - 独立解析 VCD 波形、判定仿真是否成功（退出码 0/1）
   - 检查项与测试方案/预期结果对应（事务次数、关键握手、数据比对等）
3. 确认 TB 语法与工具链匹配：**iverilog 下使用简单语法**（reg/wire/always/initial/task，
   不用 class/package/fork-join 等 iverilog 不支持或不稳定支持的语法）；仅在使用
   Questa/XSim 等完整仿真器时才允许完整 SV 验证语法

🛑 检查点：TB + 分析脚本就绪，用户确认后进入 C1

---

## C1. 编译 + 仿真

```bash
iverilog -g2012 -o <tb>.out -s <tb> <RTL 全部文件> <tb>.sv   # 编译
vvp <tb>.out                                                  # 仿真 → 生成 <tb>.vcd
```

- 编译错误 → 先分清是 RTL 还是 TB 的问题；iverilog 工具限制（如参数除法拼接
  `{W/8{1'b1}}`、寄存器无复位 X 态）按 C3 第 ② 类"工具兼容"就地绕过
- TB 内必须自带 DUT 自检（打印 ALL PASS / FAIL）作为第一道判定

---

## C2. 波形分析

1. 运行分析脚本：`python check_vcd.py <tb>.vcd`（退出码 0/1）
2. 脚本失败或 DUT 自检失败 → 定位问题：
   - gtkwave 打开波形人工观察
   - 或编写临时逐拍打印脚本（时间戳 + 信号值 base-2 解码）辅助定位
3. 分析脚本**增量演化**：每发现一类新问题，可给脚本补充一条断言

---

## C3. 问题定位与修复（四分类回退）

> **定位顺序强制：先检查 TB 和分析脚本，确认无误后再查 RTL。**

| 分类 | 判定 | 回退目标 |
|------|------|---------|
| ① TB/脚本问题 | TB 激励错误、等待错过事件、脚本解析错误 | 回 B2（TB）或就地改分析脚本 |
| ② 工具兼容 | iverilog 限制导致的伪问题（编译语法、X 态） | 就地绕过（localparam、寄存器初始化等），记录问题追踪，不改设计 |
| ③ RTL 问题 | 现象定位到 RTL 行为错误 | **回退到方案设计（A1）**：方案有必要修改 → 更新设计方案后从 A1 重新推进；方案无需修改 → 继续代码编写（A2），改前对照 A1 对应章节 |

每轮循环记录到 `doc/sim/验证报告_<模块名>.md`（"第 N 轮验证"）+ 同步问题追踪。

---

## C4. 回归

- 重跑 C1（编译）→ C2（波形分析）
- 每轮回归必须全部步骤重跑，不得跳过

---

## 终止条件

同时满足以下全部条件 → 进入 C5：
1. TB 自检 ALL PASS
2. 分析脚本全部检查通过（退出码 0）
3. 连续一轮无新问题

---

## C5. 全面检查（C 阶段收尾）

> C 阶段结束的唯一标准：C5 全面检查通过。发现问题 → 按 C3 规则回退修复 →
> 重新进入验证循环；无问题 → C 阶段结束。

**第一步：C 阶段内部一致性**

| 检查项 | 方法 |
|--------|------|
| 验证报告 ↔ 问题追踪 | 问题是否全部关闭、每条修复都有对应记录 |
| 分析脚本 ↔ 验证报告 | 脚本检查项是否覆盖验证报告声称的验证点 |
| 仿真产物 | VCD/out 是最后一遍验证生成的，结论与产物一致 |

**第二步：全项目一致性复查**（必须重跑——C 阶段可能已通过回退路径修改过
RTL/TB/文档，B7 的检查结果已过时）：
RTL ↔ 设计方案 ↔ TB ↔ sim 文档 ↔ 接口一致 ↔ README

🛑 检查点（C5 通过后）→ 生成/更新 README → 结束

## 行为准则

1. **默认手动模式**：只有用户明确说 `--auto` / "自动" / "全自动" 才进入自动模式。禁止 AI 自作主张
2. **需求没搞清楚之前禁止进入设计**：先执行 A0/B0 需求分析，追问直到需求完全理清楚，直到用户确认
3. **用户修改需求 → 立即回到 A0/B0**，更新需求文档后逐阶段重新推进
4. 启动问模式 + 判定单/多模块规模
3. 创建全部目录
4. **多模块时从底向上编写，每个模块独立审查 + 集成审查**
5. **设计文档"各模块详细说明"的编号步骤 = 代码中 `// ---- N. ----` 注释**
6. 语法解析仅关键语法
7. 迭代从设计开始，只改受影响模块
8. RTL 可综合 / Testbench 不可综合
9. 自动模式全部记录，≤3 轮迭代
10. A7 仅 RTL 检查，B7 sim 检查 + 全项目检查
11. **A3/B3 审查是循环的**：发现问题 → 修复 → 回归重审，连续一轮无新问题才通过。单次审查发现问题后直接修复并重审，不得跳过回归
12. **发现问题先查 TB 和分析脚本，确认无误后再查 RTL**（C 阶段强制定位顺序）
13. **RTL 问题默认回退方案设计**：方案有必要修改 → 更新设计方案后从 A1 重新推进；方案无需修改 → 才进入代码编写（A2）
14. **工具兼容问题就地绕过**（iverilog 限制），记录到问题追踪，不改设计
15. **C 阶段每轮循环落盘验证报告，C5 全面检查通过后 C 阶段才结束**
