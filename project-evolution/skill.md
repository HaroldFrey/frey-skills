# project-evolution — 项目迭代演进记录

记录项目每次会话/版本的修改、决策和问题，生成结构化迭代日志文档。

## 触发条件

- 手动：`/project-evolution` 或 `/project-evolution <起始版本>`（如 `/project-evolution v1.0`）
- 自动：开发会话结束时，如检测到文件变更，主动提示是否记录

自动触发提示格式：
```
📝 检测到本次会话有以下变更：
- control.sh: 新增初始 reboot
- run_all.sh: 新增参数校验
- CHANGELOG_06.md: 更新日期

是否记录到 ITERATION_LOG.md？
- 回复"是"→ 自动生成迭代记录
- 回复"详细记录"→ 交互式问答，逐项确认细节
- 回复"否"→ 跳过
```

## 参数

| 参数 | 说明 |
|------|------|
| `<起始版本>` | 可选，指定当前迭代的版本号，如 `v2.0` |
| 无参数 | 使用当前日期作为迭代标识 |
| `--detail` | 进入详细模式，逐项交互确认 |

## 记录流程

### 第零步：收集背景

1. 如项目存在 `ITERATION_LOG.md`：读取，作为追加起点
2. 如项目存在 `CHANGELOG*` / `REVIEW.md`：读取，关联已有记录
3. 读取本 skill 的 `learnings.md`，获取历史经验

### 第一步：变更扫描

1. 通过 `git diff`（如有 git）或文件时间戳对比，识别本次变更的文件
2. 对每个变更文件，分类：
   - ✨ 新增
   - 🔧 修改
   - 🗑 删除
3. 提取关键变更点（函数/配置/逻辑/文档）

### 第二步：交互确认

向用户确认并补充每个变更：
```
📋 确认以下变更记录：

1. [control.sh] 修改
   - 行 103-108：新增测试前初始 reboot
   - 行 34-48：wait_for_reboot 简化为固定 10s 轮询
   - 决策原因：[请补充]
   - 影响范围：[请补充]

2. [run_all.sh] 新增
   - 顶层统筹脚本，串联测试与统计
   ...

确认内容？需要补充"决策原因"或"影响范围"吗？
```

详细模式下逐条确认；标准模式下确认整体。

### 第三步：问题追踪更新

如有正在进行的问题追踪条目：
```
🔍 以下问题条目状态需要更新：
- P-001：wait_for_reboot 递增退避 → 已在本次会话中关闭（简化为固定 10s）
- P-002：缺少顶层统筹 → 已在本次会话中关闭（新增 run_all.sh）

确认更新？（回复"是"/"修改后确认"/"跳过"）
```

### 第四步：生成图表

根据变更内容，生成 ASCII 图表。

**架构变更图**：如本次变更涉及架构调整，生成前后对比图。
```
迭代前                          迭代后
───────                         ───────
control.sh                      run_all.sh（新增）
  └─► cmd_time.sh                 ├─► control.sh
                                  │     └─► cmd_time.sh
                                  └─► parse_test_log.sh
```

**流程演进图**：如本次变更涉及流程调整，展示演进。
```
迭代前：task → task → task（无初始 reboot）
迭代后：reboot → task → reboot → task → reboot（全程隔离）
```

### 第五步：生成/追加 ITERATION_LOG.md

生成迭代条目，追加到项目根目录的 `ITERATION_LOG.md`。

格式模板：
```markdown
## 🏷️ 迭代 — <版本号或日期>

> 日期：YYYY-MM-DD | 会话摘要：<一句话>

### 📋 变更清单

| 文件 | 操作 | 变更说明 |
|------|------|---------|
| control.sh | 🔧 修改 | 新增初始 reboot；简化 wait_for_reboot |
| run_all.sh | ✨ 新增 | 顶层统筹脚本 |
| CHANGELOG_06.md | 🔧 修改 | 更新日期 + run_case.sh 说明 |

### 🔧 变更详解

#### control.sh

| 行号 | 变更 | 改前 | 改后 | 决策原因 |
|------|------|------|------|---------|
| 103-108 | 新增初始 reboot | （无） | `$SSH "reboot"` + `wait_for_reboot` | 确保首个任务在干净环境执行 |
| 34-48 | 简化轮询 | 递增退避 5s→30s | 固定 10s | 逻辑更直观，维护简单 |

#### run_all.sh

| 变更 | 说明 | 决策原因 |
|------|------|---------|
| ✨ 新增文件 | 顶层统筹，3 步流程（测试→取日志→统计） | 串联测试与统计，一键完成全流程 |

### 🗺️ 架构变更

```
迭代前：                    迭代后：
control.sh                  run_all.sh
  └─► cmd_time.sh             ├─► control.sh
                              │     └─► cmd_time.sh
                              └─► parse_test_log.sh
```

### 🔄 流程演进

```
迭代前：task → task → task（无初始隔离）
迭代后：reboot → task → reboot → task → reboot
```

### 🔍 问题追踪

| 编号 | 状态 | 描述 |
|------|------|------|
| P-001 | ✅ 已关闭 | wait_for_reboot 递增退避 → 简化为固定 10s |
| P-002 | ✅ 已关闭 | 缺少顶层统筹 → 新增 run_all.sh |
| P-003 | 🔴 进行中 | 配对行数检测未实现 |

---
```

### 第六步：经验沉淀

迭代记录完成后，检查是否有值得沉淀到 `learnings.md` 的经验：

- **流程改进**：记录流程中可优化的步骤
- **常见遗漏**：反复出现但容易忘记记录的内容
- **用户偏好**：图表风格、详略程度等

提议格式：
```
📝 建议沉淀到 project-evolution 的经验：
1. [常见遗漏] <描述>
2. [用户偏好] <描述>

确认写入 learnings.md？
```
⚠️ 必须经用户确认后才写入。无可沉淀经验则跳过。

## 行为准则

1. **变更不遗漏**：所有修改过的文件都应纳入变更清单
2. **决策必记录**：每个重要变更必须有"决策原因"字段
3. **图表必更新**：架构或流程有变时，必须生成前后对比图
4. **问题追踪联动**：主动检查并更新已有问题条目的状态
5. **确认不跳过**：第二步交互确认不可跳过（标准模式整体确认，详细模式逐条确认）
6. **经验需确认**：第六步经验写入必须经用户确认
