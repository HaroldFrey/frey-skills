# 需求分析

> **需求没搞清楚之前，不做任何设计和编码。需求错了，后面全错。**

这是一个独立的预处理 skill，专注于**通过不断追问将模糊需求转化为清晰的文档**。

---

## 适用场景

- 项目启动前，需求还不明确
- 用户只有一句话需求，需要展开
- 方案评审前，需要正式的需求文档
- 可嵌入其他 workflow skill 的初始阶段

---

## 执行流程

### 步骤 1：理解初始需求

根据用户最初的需求描述，整理出已有信息和缺失信息。

### 步骤 2：不断追问

**不限轮次，不限每次问题数量**，持续追问直到以下维度全部清晰：

| 维度 | 要追问到何种程度 |
|------|----------------|
| **功能** | 每个功能点都有明确的输入/输出/行为描述 |
| **接口** | 所有外部信号/参数都有名称、类型、范围 |
| **性能** | 吞吐量/延迟/频率等指标有具体数值或范围 |
| **边界** | 极端情况、异常情况如何处理 |
| **约束** | 平台、依赖、标准、编码规范等限制 |
| **优先级** | 哪些是必须的（🔴高），哪些是可选的（🟢低） |

### 步骤 3：生成需求文档

当所有细节明确后（用户说"可以了"），生成需求文档。文档格式：

```markdown
# 需求分析 — <项目名>

## 项目目标
<一句话 + 一段展开>

## 功能需求
| 编号 | 功能 | 优先级 | 说明 |
|------|------|:--:|------|
| F-001 | ... | 🔴高 | ... |

## 接口规格（如适用）
| 信号/参数 | 类型/位宽 | 方向/默认值 | 说明 |
|----------|----------|-----------|------|

## 非功能需求
| 编号 | 需求 | 要求 |
|------|------|------|

## 约束条件
- 平台 / 依赖 / 标准

## 用户确认
- [ ] 功能需求完整无遗漏
- [ ] 接口定义正确
- [ ] 约束条件准确
- [ ] 确认后进入设计阶段
```

### 步骤 4：用户确认 🛑

> ⚠️ **必须等待用户明确确认后才能结束。AI 不得自行认为需求已理清。**

用户说"通过"或"确认"后，skill 结束。后续可衔接 `/bash-dev-workflow` 或 `/sv-dev-workflow` 的设计阶段。

---

## 行为准则

1. **追问是第一要务**——宁可多问，不要遗漏
2. **每轮问题聚焦**——让用户容易回答，不要一次扔出一堆无关问题
3. **总结已有信息**——每轮追问前先简短总结已知内容
4. **用户确认是强制环节**——不受任何自动模式影响
5. **如果用户说"先这样"**——记录尚未明确的点，标注为"待确认"
