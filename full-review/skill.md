# full-review — 项目全面审查

对指定目录下的代码和文档进行系统化审查，输出分级报告。

## 触发条件

- 手动：`/full-review` 或 `/full-review --focus <文件>`
- 自动：用户消息包含"检查""详细检查""review""全面检查""代码审查"等关键词

## 参数

| 参数 | 说明 |
|------|------|
| `--focus <文件>` | 只审查指定文件（可多次指定），如 `/full-review --focus control.sh --focus run_all.sh` |
| `--auto` | 审查完成后自动修复发现的问题（**仍需二次确认**，见下方行为准则第 7 条） |
| 无参数 | 审查当前项目目录下所有脚本和文档 |

## 审查流程

### 第零步：收集背景信息

1. 扫描目标目录下的所有文件，识别项目类型：
   - `.sh` 文件为主 → Bash 项目 → 调用 `/bash-defensive-patterns`
   - `.v` / `.sv` 文件为主 → Verilog 项目 → 调用 `/verilog-sv-language` + `/vivado-synth`
   - `Makefile` 存在 → 调用 `/makefile-patterns`
   - 混合项目 → 综合调用上述 skill
2. 如项目存在 `REVIEW.md`：读取，了解历史问题及其解决状态，避免重复报告
3. 如项目存在 `CHANGELOG*` 或版本记录文件：读取，了解最近变更范围，重点审查变更区域的连带影响
4. 如以上文件均不存在，正常审查，不做增量判断
5. 读取本 skill 目录下的 `learnings.md`，获取历史经验：审查清单补充项、已知误报/免检项、用户偏好

### 第一步：代码审查

对每个脚本文件检查：

- **逻辑错误**：死循环、条件分支遗漏、变量未初始化
- **边界问题**：空输入、文件不存在、glob 无匹配、退出码丢失
- **set -e/pipefail 交互**：`$?` 捕获是否被 `set -e` 阻断、管道失败是否被 `pipefail` 隐藏
- **变量引用**：是否缺少引号、`$@` vs `$*`、未定义变量
- **错误处理**：关键命令的退出码是否被检查、scp/ssh 失败后的行为
- **脚本间契约一致性**：
  - 同一配置值在多个脚本中是否一致（如 TARGET、SSH_PORT）
  - 退出码约定是否对齐（A 脚本产出的退出码，B 脚本是否正确处理）
  - 文件路径/目录结构约定是否一致

### 第二步：文档审查

对每个文档文件（`.md`、`.txt`）检查：

- **配置值一致性**：文档中引用的默认值、超时参数等是否与实际代码一致
- **行号引用**：文档中引用的行号（如 `control.sh:89`）是否与当前代码实际行号匹配
- **流程描述**：文档描述的步骤、调用顺序是否与实际代码逻辑一致
- **新增功能覆盖**：代码中新增的功能/配置项在文档中是否有对应说明

### 第三步：交叉一致性

- 多个脚本引用的同一配置项是否一致
- 文档中的架构图是否反映实际调用关系
- 文档中的示例命令是否与实际用法一致

### 第四步：CHANGELOG 一致性（如有）

- CHANGELOG 中记录的变更是否与实际代码差异一致
- 实际代码中存在但 CHANGELOG 未记录的变更
- CHANGELOG 中提到的被删除/替换的功能是否确实不存在了

### 第五步：经验沉淀（审查报告输出后执行）

审查报告输出完毕后，检查本次是否有值得沉淀的经验。满足以下任一条件时，向用户提议追加到 `learnings.md`：

- 发现了一个**新的常见问题模式**（可加入审查清单）
- 某个检查项**被证实为误报**（可加入免检列表）
- 用户表达了**审查风格偏好**（如"太啰嗦""以后忽略这类"）

提议格式：
```
📝 建议沉淀的经验：
1. [类型：审查清单补充] run_all.sh 缺少 set -E → 后续审查自动检查
2. [类型：误报/免检] $SSH "reboot" 不检查退出码 → 有 wait_for_reboot 兜底，后续跳过

追加以上内容到 learnings.md？
- 回复"是"/"确认"→ 全部写入
- 回复"只加 X"→ 选择性写入
- 回复"否"→ 跳过
```
⚠️ **必须等待用户明确确认后才写入 learnings.md。** 不等回复就写入是不允许的。如本次无可沉淀经验，跳过此步骤。

## 输出格式

### 终端输出

按严重程度分组，每组内按文件/位置排列：

```
═══════════════════════════════════════════════════
  Full Review — <项目目录>
  日期：YYYY-MM-DD
  范围：文件数 X（代码 Y + 文档 Z）
═══════════════════════════════════════════════════

🔴 严重（X 个）
─────────────────────────────────────────────
[文件路径:行号] 问题简述
  当前代码：<代码片段>
  问题分析：<为什么有问题>
  修复方案：<具体修改前后对比>
  来源：代码审查 / 脚本间契约 / CHANGELOG 对照 / ...

🟡 中等（X 个）
─────────────────────────────────────────────
  ...

🟢 低（X 个）
─────────────────────────────────────────────
  ...

📊 汇总
─────────────────────────────────────────────
总计 X 个问题：🔴 X · 🟡 X · 🟢 X
建议优先处理 🔴 严重 项
```

### 文件输出

同步写入 `REVIEW_report_YYYYmmdd_HHMMSS.md`（与项目 REVIEW.md 同目录或审查目录下），格式同上，方便归档和后续跟踪。输出完成后提示文件路径。

## 分级标准

| 级别 | 判定条件 |
|------|---------|
| 🔴 严重 | 运行期必定出错（如变量未定义导致脚本崩溃）、数据丢失风险、安全漏洞、文档与实际行为完全矛盾 |
| 🟡 中等 | 边界条件下出错（如空目录导致脚本意外退出）、配置不一致、文档描述过时、缺少错误处理 |
| 🟢 低 | 代码风格、注释不清晰、文档格式、可选的改进建议 |

## 行为准则

1. **默认只报告不修改**：审查完成后仅输出报告，严禁自动编辑任何被审查文件。修复方案放在"修复方案"字段中供用户参考
2. **每个问题附修复代码**：必须是 `old → new` 的具体 diff，不能是笼统的"建议修改 XX"
3. **关联已有记录**：如项目有 REVIEW.md，标注哪些是已知但未修的问题，哪些是本次新发现
4. **聚焦审查优先**：`--focus` 模式下仅审查指定文件，但**脚本间契约一致性**检查不受限制（需要跨文件对比）
5. **项目类型自适应**：自动识别并调用相关 skill，不强制用户指定
6. **覆盖范围宁多勿少**：不确定是否算问题时，仍然报告（标注为低严重度）
7. **自动修复需二次确认**：以下任一情况，审查完成后须明确询问用户是否要执行修复 ——
   - 用户使用了 `--auto` 参数
   - 用户说了"检查并修改""自动修复""review and fix"等类似表述
   
   确认格式：
   ```
   📋 共发现 X 个问题，修复涉及 Y 个文件。确认执行自动修复？
   - 回复"是"或"确认"→ 立即修改
   - 回复"否"或"取消"→ 仅保留报告，不做修改
   - 回复"选择性修改，修复 X1、X3..."→ 只修改指定项
   ```
   ⚠️ **必须等待用户明确回复后才执行修改**，不等回复就修改是不允许的
8. **经验沉淀需用户确认**：审查完成后，如发现可沉淀的经验（新问题模式、误报项、用户偏好），向用户提议追加到 `learnings.md`，提供明确的"是/否/选择性"选项。必须经用户确认后才写入。不可盲目自动写入
9. **修复后必须更新审查报告记录修复情况**：用户同意修复且 AI 完成修复后，必须在原 `REVIEW_report_*.md` 中记录本次修复 ——
   - 在每个已修复问题的条目下追加 **修复记录**（修复日期、修复内容摘要、涉及文件），并将该问题的**状态标记为 `[已修复]`**
   - 未修复/用户拒绝的问题保留原状，状态标记为 `[未修复]`（可注明原因）
   - 如有修复中发现的新问题或遗留风险，追加到报告末尾"修复遗留"小节
   - 修改报告时保持原始问题描述与修复方案不变（可追溯），只追加修复记录
